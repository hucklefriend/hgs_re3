# 検索流入の整備・旧URL救済・探索アクセス対策

作成日: 2026-09-09
状態: 未実装。GPT-5.6 Solへの実装引き継ぎ用。

## 1. 目的と背景

HGNは個人運営で約20年の履歴があり、当面の収益目標はサーバー・ドメインの維持費（月1,000円弱）。まずデータベースへの検索流入と過去のリンクを活かし、作品情報に到達できる状態を整える。広告・アフィリエイト・課金機能そのものは今回の対象外。

HTTPSアクセスログ（2026-09-01〜09、端の日は一部の可能性あり）を解析したところ、次を確認した。

| 観測 | 件数・内容 | 対応目的 |
|---|---|---|
| 総リクエスト | 17,250件、200応答7,287件 | ボットを含み、PVや利用者数とは区別する |
| 404 | 9,037件 | 探索アクセスと救済すべき旧URLを分ける |
| `/sitemap.xml` | 404が121件 | 検索エンジンが公開ページを発見する経路を用意 |
| 旧画像 | `/img/banner.jpg` 30件、`/images/banner/all1.gif` 15件、`/images/banner/muji.gif` 4件 | 過去のバナー参照を復旧または登録元で修正 |
| 旧ページ | `/game/soft/52`、`/game/soft/115?gb=1`、`/game/search`等 | 現行URLへ転送 |
| 探索アクセス | WordPress関連、`.env`、`.git/config`等 | 不要なPHP処理・DB処理・転送を減らす |

元資料はローカルの `/var/tmp/access_log/report.html` と同フォルダのHTTPSログ。将来上書きされる可能性があるため、上記は今回の観測値として扱う。生ログ・IP・個人情報をGitへ追加しない。

Google参照元から作品ページを開きCSS/JSも取得する例があるが、人間であることや人数は確定していない。参照元・User-Agentは偽装可能。サイトマップ不在が流入低迷の原因だと断定しない。

## 2. ユーザーから確定している事項

- `/game/soft/{id}` の数値は **`game_titles.id`**。DBから現行の`key`を取得して転送する。別のID対応表は不要。
- バナー画像は過去参照。画像の再設置、または昔登録した検索サイト側の登録修正のどちらも候補。
- 今回は計画書のみ。実装担当者はこの文書を元に作業する。
- 実装時もリポジトリのAGENTS.mdを遵守する。マイグレーション操作は実行せず必要時にコマンドを提示する。pushはユーザーに委ねる。
- `docs/old/` は読まない。旧仕様はユーザーの説明・現存ログ・現行コードから確認する。

## 4. 実装順序

1. 公開URL・年齢確認・正規ホスト・本番配信構成を確認。
2. サイトマップとrobots.txtの案内を実装。
3. 旧作品URL・旧検索URLの転送を実装。
4. 明確な探索パスをWebサーバーで早期拒否。
5. バナー復旧または登録元修正を進める。素材・外部アカウント待ちは他作業を止めない。
6. テスト・ステージング検証・運用資料を完成させる。
7. 公開後に検索エンジンへの登録確認とHTTPSログの再集計。

## 5. サイトマップ

### 掲載範囲

初回は次の明示的な一覧を対象にする。全ルートの自動列挙やサイト全体のHTTPクロールで生成しない。

- トップ、ゲームラインナップ。
- 公開中で正常に到達できる作品詳細、フランチャイズ詳細、プラットフォーム一覧・詳細。
- メーカー、メディアミックス、お知らせ、レビュー等の拡張は初回の必須範囲にしない。
- 検索結果クエリ、ページネーション、旧URL、ログイン・登録・管理・ユーザー専用画面、問い合わせトークン、APIを掲載しない。
- `key`が空、不正、正規URLで公開できないレコードを除外。公開条件は現行詳細ページと揃える。
- 年齢確認対象も現行仕様に従う。`over18=1`をサイトマップに付けない。年齢確認ページの応答・インデックス方針を確認して、確認画面しか出ない対象は初回掲載を保留し、その条件を資料に明記する。クローラー専用の確認回避は実装しない。

### 構成と生成

- `GET /sitemap.xml`でUTF-8 XMLを返す専用Controller/Serviceを追加。HTMLレイアウトや通常画面の`tree()`等を経由させない。
- 小規模なら単一`urlset`と短期キャッシュ（初期案1時間）で開始。事前に件数とサイズを確認し、上限を超える場合はindexと分割ファイルにする。黙って切り捨てない。
- 1ファイル50,000 URL、非圧縮50MBの上限、XML名前空間、エスケープは[Sitemapsプロトコル](https://www.sitemaps.org/protocol.html)に従う。
- DB取得は必要カラムに絞り、大量取得時はチャンク処理。公開ページ生成や関連データ全取得によるN+1を避ける。
- URLは名前付きルートの相対パスと信頼する設定上の公開ベースURLから組み立てる。本番は`https://horrorgame.net`。リクエストのHostヘッダーでサイトマップ内のホストが変わらないようにする。
- staging/localは環境設定に従い、本番URLが混ざらないようにする。環境をまたぐキャッシュキーも避ける。
- `lastmod`はページの実変更日時を信頼できるときだけ出す。生成時刻を全URLに入れない。関連テーブル変更まで追えていなければ初回は省略してよい。
- `priority`、`changefreq`は初回不要。
- Content-Typeは`application/xml`。デバッグ出力やセッション依存データが混入しないことを検証する。
- キャッシュで追加・削除・key変更が最大1時間遅れる仕様と、即時更新方法を記録する。キャッシュ基盤は既存設定に合わせ、新しい常駐サービスは導入しない。

### robots.txt

- `Sitemap: https://horrorgame.net/sitemap.xml`を案内する。
- 現在の静的`public/robots.txt`を維持するか、環境別生成へ変えるかは配信構成に合わせる。動的ルート化する場合、静的ファイルが先に配信される競合を解消する。
- stagingの公開制御を弱めない。本番URLを一律で案内する環境混在を避ける。
- robots.txtを不正アクセスの防御手段として使わない。

## 6. 旧URL転送

専用の小さなController（例: `LegacyGameRedirectController`）にまとめ、GET/HEADだけを対象にする。

### `/game/soft/{id}`

1. 正の整数のIDだけを受け付ける。非数値、0、負数、極端に長い数値は404にし、DBへの不正な型変換を避ける。
2. `GameTitle`を主キーで取得し、現在の`key`を得る。
3. `Game.TitleDetail`（`titleKey`パラメータ）へ301を返す。文字列の置換でslugを推測しない。
4. ID不存在、公開不可、利用できるkeyなしは404。トップへ一律転送して成功扱いにしない。
5. `gb=1`等の旧表示クエリは破棄する。任意の`url`、`redirect`、`next`、`over18`も引き継がない。年齢確認は転送先の既存処理に任せる。
6. 転送先は同一サイトの正規URLに限定し、リクエストHostやクエリから任意の転送先を作らない。
7. `/game/soft/52/`も最終的に到達することを確認。アプリ側では一段の転送とし、既存のHTTP→HTTPS・末尾スラッシュ正規化による追加段数は配信環境で確認する。

### `/game/search`

- 検索なしの旧URLは`Game.Lineup`へ301。
- 現在の検索語パラメータは`text`。旧ログに検索語付きの例があるか調べ、確認できた旧パラメータのみ`text`へ変換する。`q`や`keyword`を旧仕様と推測して無制限に対応しない。
- 旧パラメータが確認できなければ、初回は`text`の単一文字列のみ維持し、それ以外は破棄する。検索語付きの旧仕様が未確認であることを運用資料に残す。
- 配列や長すぎる検索語は安全に扱い、URLエンコードする。現行検索の入力制限を確認して上限を揃える。
- 旧ページ番号・旧プラットフォームID等は意味の対応が確定するまで引き継がない。

`/game/favorite/{id}`、`/game/title/B00B7QZMG8`等は今回の対応表に含めない。ログに出ただけでは意味や対応が確定しないため、404を維持して別途調査する。

## 7. 過去バナー

優先対象は`/images/banner/all1.gif`、`/images/banner/muji.gif`、`/img/banner.jpg`。

1. 現在の公開素材・ユーザー提供素材に利用可能なバナーがあるか確認する。`docs/old/`は調査しない。
2. 既存素材を再利用できる場合は旧パスに画像を再配置、または対応する現行画像へ301。拡張子・MIME・画像寸法・外部埋め込み時の表示を確認する。
3. 素材がなければ新しいバナーを勝手に作らず、必要な素材・寸法をユーザーに確認する。HTMLのトップページへ画像URLを転送しない。
4. 元ログのRefererと画像パスを照合し、登録元候補を整理する。ドメイン名の集計だけで参照元を断定しない。
5. 検索サイトの登録変更が必要なら、変更するサイトURL・現在の登録内容・新しいURLを一覧化する。外部アカウントの編集や相手への連絡は本計画の実装作業に含めず、ユーザーによる対応項目として渡す。

素材待ちの項目は未完了理由を明記し、勝手な代替画像で完了扱いにしない。

## 8. 探索アクセス対策

### 方針

リクエストの存在だけで侵害とは判断しない。今回の目的は、明らかにこのアプリで使わないパスをPHPに渡さず安価に拒否し、正規ユーザーと検索クローラーが使う経路を保つこと。全ボット排除や全404排除は目標にしない。

初回はApache側の限定的なルールを基本とする。VirtualHostまたは利用が確認できた`public/.htaccess`で、末尾スラッシュ転送・フロントコントローラー処理より前に評価する。[Apache公式のアクセス制御例](https://httpd.apache.org/docs/2.4/rewrite/access.html)を参照し、設定位置によるパターンの違いを検証する。

### 初回の拒否対象候補

- `.env`および明確なバックアップ変種、`.git`配下などの秘密情報探索。パス要素の境界を設け、通常の文字列の一部に誤一致させない。
- `/wp-login.php`、`/wp-admin`、`/wp-content`、`/wp-includes`、`/wp-json`とその配下。
- ログで確認した`/wp/`、`/wordpress/`、`/blog/`下のWordPress専用パス。`/blog`全体の禁止に広げない。
- `rest_route`によるWordPress API探索はクエリ側で別に判定。現行コードで使っていないことを再確認し、少なくとも観測された`/batch/v1`の変種を扱う。

拒否ステータスは初回403に統一し、小さなサーバー標準応答または静的応答にする。ErrorDocument設定によってLaravelのエラーページへ戻らないことを必ず確認する。拒否時にDB・セッション・通知処理を起動しない。

### 誤検知防止・対象外

- `/.well-known/acme-challenge/`等、証明書更新に必要な経路を保つ。すべてのドットパスを一括拒否しない。
- `/index.php`、`/admin`、通常のログイン、OAuth callback、API、画像、robots.txt、サイトマップ、旧URL転送を壊さない。
- PHP拡張子をすべて禁止しない。User-Agent・Refererの有無だけで拒否しない。
- 記録に出たIPや国を固定で禁止しない。検索クローラーの名乗りだけを信用して無制限に許可もしない。
- 一般閲覧への一律の厳しいレート制限、CAPTCHA、WAFサービス導入は初回対象外。
- URLの大文字小文字、重複スラッシュ、エンコード変種をテストする。網羅的な攻撃検知エンジンは自作せず、対応範囲を記録する。

### 第2段階: 必要なら一時的IP制限

早期拒否後もサーバー負荷・ログ量が問題になる場合だけFail2ban等を検討する。初回では自動BANを有効化しない。

- 「一定時間内に複数回、明確な探索パスへアクセス」を対象にし、全404をBAN条件にしない。
- CDN・リバースプロキシ経由なら信頼境界と実IP記録を先に確認する。転送ヘッダーを無条件に信用しない。
- まず既存ログで検出のみ行い、正常経路が該当しないか確認して閾値を決める。
- 有効期限付きBAN、管理接続の保護、解除方法、停止方法を用意してから運用変更として扱う。

## 9. 検証・受け入れ条件

### Laravel Featureテスト

- サイトマップ: 200、XML解析成功、名前空間、Content-Type、掲載対象と除外対象、URL重複なし、公開ホスト固定、XMLエスケープ。
- key変更・追加・削除がキャッシュ期限または明示的な更新後に反映される。サイズ上限への対応を検証する。
- 旧作品: 既存IDから正しいkeyへの301、HEAD、存在しないID・非数値・巨大IDの404、旧クエリの破棄、外部転送不可、年齢確認の非回避。
- 旧検索: クエリなし、許可した検索語、日本語・記号、配列・過長値、未知クエリの破棄。
- 既存の作品詳細・ラインナップの関連テストを実行し、回帰がないことを確認する。

テストDBが本番ではなく専用のものであることを確認。マイグレーション操作は禁止事項に従い、必要ならユーザーにコマンドを渡す。キャッシュ生成コマンドは同じシェルで先に`umask 0002`を設定する。

### Apacheを通した検証

PHPのFeatureテストや`artisan serve`では`.htaccess`は検証できない。ローカルのApacheまたはステージングで別途行う。

- 設定構文検査に加え、実リクエストで探索パスが403となることを確認する。
- クエリ付き、末尾スラッシュ付き、大文字小文字・重複スラッシュ等を含む観測例を再現する。
- 正常URL・API・認証・静的ファイル・ACME・サイトマップ・旧URLの応答が維持される。
- アプリログ/PHP側の記録等で、拒否リクエストがLaravelへ渡っていないことを確認する。
- 本番ホストで200/301/403/404の役割を確認。旧ページ不存在は404のまま、対応のある旧ページだけ301にする。

### 公開後

- Search Consoleでサイトマップを送信・取得確認する。これは外部アカウントでの運用作業としてユーザー向け手順を用意する。
- 同程度の期間のHTTPSログで、旧URLの301、サイトマップ200、探索パス403、正常な作品ページへのアクセスを比較する。
- 404総数だけを改善指標にしない。403へ変わった数と、PHPまで届く探索アクセスの減少を区別する。
- サイトマップによる検索順位・アクセス増を完了条件にしない。索引登録や流入は公開後の観測対象。

## 10. 成果物とロールバック

想定する変更先（命名・分割は既存規約に合わせてよい）:

- `routes/web.php`、サイトマップController/Service、旧URL転送Controller。
- 必要に応じたサイトマップ設定・XML出力用ファイル、`public/robots.txt`。
- `public/.htaccess`またはレビュー可能なサーバー設定差分と適用手順。
- 確保できたバナー画像、関連Featureテスト。
- `docs/Codex/`の運用資料: 掲載対象、更新方法、旧URL対応表、遮断ルール、検証方法、登録元の対応状況。
- Artisanコマンドを追加・変更する場合は`docs/Codex/artisan-commands.md`も更新。初期案では専用コマンドやマイグレーションは必須でない。

段階ごとにレビューできる差分にする。本番設定を変更する場合は元設定と復元手順を残し、構文検査・ステージングでの確認後に運用手順に従って反映する。探索遮断ルールだけを外せる構成にし、誤検知時にURL救済やサイトマップまで戻す必要がないようにする。301はクライアントにキャッシュされ得るため、転送先を公開前に十分検証する。

完了報告では、実装内容・原因と修正方法・テスト結果・本番への未反映項目・バナーや外部登録の未対応項目を明記する。コードが完成しても外部登録が残っている場合は、全体完了と混同しない。
